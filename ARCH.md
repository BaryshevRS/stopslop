# StopSlop — ядро продукта

Позиционирование: линтер проверяет, *как* написан код. StopSlop проверяет,
*не наплодил ли агент лишнего* — переусложнённые функции, свалку несвязанных
ответственностей в одном файле/классе, а на этапе 2 — дубли и мёртвый код.
Не конкурент ESLint/Biome: ни одного стилевого или типового lint-правила.

Два целевых кейса (наблюдаемое поведение LLM-агентов):

1. **Псевдосвязный монстр** — один core-класс/модуль на 2k строк, ответственности
   смешаны, но формально всё связано через пару общих полей (`state`, `config`).
2. **Свалка** — агент валит все классы, функции и константы в один файл,
   не видя структуры проекта.

Оба кейса покрываются одним движком связности (см. ниже): свалка распадается
на кластеры сразу, монстр — после снятия хабов.

---

## Пайплайн

```
discover ──► parse (oxc) ──► per-file analyzers ──► detectors ──► findings ──► report
  фильтры     1 AST/файл      complexity              god module     ключ:       terminal
  ignore      shared          members+refs            god class      file+symbol  --json
                              cohesion graph                         (baseline)
```

- `oxc-parser` — прямая зависимость, один `parseSync` на файл, AST раздаётся
  всем анализаторам (complexity и извлечение членов идут в одном обходе).
- Анализаторы этапа 2 (Clone Alert, Knip session API) входят через
  `analyzeProject(ctx)` — ядро от них не зависит.
- Каждый `Finding` сериализуется с идентичностью `file + symbol` — на этом
  строится diff/baseline этапа 3.

## Модель данных

```ts
interface Member {
  name: string;
  kind: 'function' | 'state' | 'dependency';
  complexity: number;      // cognitive, из общего обхода
  refs: Set<string>;       // члены той же единицы, которые он трогает
  exported: boolean;
  loc: number;
}

interface CohesionUnit {           // модуль ИЛИ класс — движок один
  kind: 'module' | 'class';
  members: Member[];
  clusters: string[][];            // компоненты связности после хабов
  hubs: string[];                  // снятые хаб-члены
}
```

## Анализаторы: что откуда взято

### Cognitive complexity — порт по спецификации

- **Теория/спека**: G. Ann Campbell (SonarSource), white paper
  *Cognitive Complexity: A New Way of Measuring Understandability* —
  формальная спецификация (инкременты, штраф за вложенность, краевые случаи).
- **Код-референс**: правило `cognitive-complexity` в `eslint-plugin-sonarjs`.
  ⚠️ LGPL — портируем по спеке, код не копируем; их результаты используем
  как эталон в тестах на общих фикстурах.
- **Эвристики**: нет. Метрика детерминированная, порог (дефолт 15) — общепринятый
  дефолт Sonar, уточняется калибровкой.
- **Решения реализации** (этап 1):
  - **Рекурсию НЕ считаем.** White paper относит рекурсию к фундаментальным
    инкрементам, но `eslint-plugin-sonarjs` (наш оракул для сверки) её не
    учитывает — считаем как он, иначе числа не совпадут. Все примеры из white
    paper совпадают до единицы.
  - **Гранулярность отчёта:** сложность считается per-функция, но вложенные
    функции/колбэки **сворачиваются во владельца** (top-level функция или метод),
    а не репортятся отдельно. Sonar репортит и вложенные; мы — нет: для слоп-
    отчёта важна суммарная сложность единицы, а не шум из анонимных колбэков.
    Имена: `Class.method`, имя функции, имя arrow-const; анонимные не репортятся.
  - `if`/`else if`/`else` в ESTree — это вложенные `IfStatement` в `alternate`;
    `else if` получает плоский +1 (без штрафа вложенности), тело — на уровень глубже.

### Движок связности — LCOM4

- **Теория**: Hitz & Montazeri, *Measuring Coupling and Cohesion in
  Object-Oriented Systems* (1995). Наш «граф членов, компоненты связности =
  кластеры» — это дословно их LCOM4, включая исключение конструктора.
  Корни модульной связности — Stevens/Myers/Constantine (structured design, 1974).
- **Прецедент «кластеры = план распила»**: JDeodorant — Fokaefs, Tsantalis и др.,
  *Decomposing object-oriented class modules using an agglomerative clustering
  technique* (ICSM 2009): находят god class и предлагают конкретные Extract Class.
  Если компоненты связности окажутся слишком грубыми — их агломеративная
  кластеризация запасной вариант.
- **Наши инженерные решения** (не из литературы, помечаем явно):
  - **`dependency`-члены не создают рёбер** (DI-поля класса, импорты модуля).
    Мотивация: два метода, использующие один инжектированный сервис, — это не
    связность, это DI. Лечит главный источник вранья ATFD в TypeScript.
  - **Хаб-исключение** — ЭВРИСТИКА. Член с fan-in > 50% снимается из графа,
    компоненты пересчитываются. Опубликованного правила с таким порогом нет;
    документированная проблема — LCOM-семейство критикуют за то, что общие
    атрибуты склеивают любую структуру (наш кейс «псевдосвязный монстр»).
    Строгий аналог — community detection (Girvan–Newman); хаб-исключение —
    его дешёвая детерминированная аппроксимация. Порог 50% — прикидка до
    калибровки. Снятые хабы не прячем, а репортим: «связность держится на: …».
  - **Содержательные группы (≥2) vs одиночки** — ЭВРИСТИКА, выявлена при
    реализации. Чистый LCOM4 на фасаде/адаптере даёт «31 группа», где 26 —
    одиночные делегирующие методы (`disable`, `enable`, `status`…). Это
    техническая правда, но бесполезна как «границы распила» и подрывает доверие.
    Кластеры делим на **группы ответственности (≥2 члена = реальные границы)** и
    **одиночек** (сворачиваем в счётчик). Гейт god-детектора считает именно
    группы, не сырые компоненты. Пример: `ExpressAdapter` из nest —
    «41 метод в 4 группах (+27 одиночек)» вместо «31 группа».
  - **Вырождение на малых единицах.** При хаб-исключении любое единственное
    общее поле в классе из 3 методов (напр. `Stack` над `items`) помечается
    хабом → методы «распадаются». Это неизбежное свойство LCOM-семейства на
    мелочи (та же проблема, что у TCC). Лечится не логикой движка, а **гейтом по
    числу членов** (`minMembers`): `Stack` никогда не доходит до детектора.

### God Class

- **Теория**: термин — Riel, *Object-Oriented Design Heuristics* (1996).
  Detection strategy («WMC высокий И ATFD > 5 И TCC < 1/3») — Marinescu,
  *Detection Strategies: Metrics-Based Rules for Detecting Design Flaws*
  (ICSM 2004); книга Lanza & Marinescu, *Object-Oriented Metrics in Practice* (2006).
  Метрики: WMC — Chidamber & Kemerer (1994); TCC — Bieman & Kang (1995);
  ATFD — Marinescu (начало 2000-х).
- **Код-референс**: `GodClassRule` в PMD (открытый Java-исходник, включая
  ATFD/TCC/WMC).
- **Наше отклонение от PMD** (осознанное): гейт WMC/ATFD/TCC **не портируем**.
  Причины: (а) ATFD без type checker'а не отличает «лезет в чужие данные» от
  DI — в Angular ATFD > 5 у любого сервиса; (б) TCC вырожден на классах < 3
  методов и искажается конструкторами/lifecycle-хуками; (в) пороги
  WMC ≥ 47 / ATFD > 5 / TCC < 1/3 откалиброваны на корпусе 45 Java + 37 C++
  проектов — на TS распределения другие. Берём у Marinescu **идею
  комбинированной detection strategy**, не константы.
- **Две оси детекции (OR) — ключевое решение, найдено на реальных репо:**
  - **Дисперсия** (движок LCOM4): «членов много И групп ≥ 3 И Σ сложности
    высокая». Ловит класс, распадающийся на несвязанные ответственности, —
    и даёт **чистые границы распила**. Пример: `ExpressAdapter`/`FastifyAdapter`
    в nest (4 и 3 группы).
  - **Размер / WMC** (без когезии): «методов очень много И Σ сложности
    огромная». Ловит **монолит, который честно связан, но 2к строк перебор** —
    ровно тот кейс, что генерит LLM: всё завязано на общий `state`, единый
    компонент связности, хабов нет. Когезия такой класс **не может и не должна**
    разбивать (связи настоящие), поэтому размер — **отдельная ось**. Это в
    чистом виде WMC-сигнал Marinescu (Σ сложности методов).
  - **Почему обе нужны:** прогон на репо пользователя показал, что детектор
    только на дисперсии **пропускал** `CodeloreService` (60 методов, WMC 402,
    1 кластер) и `AngularIndexer` (89 методов, WMC 341). Дисперсия молчала —
    класс «честно связный». Ось размера их ловит и **честно сообщает**:
    «densely coupled — автоматических границ нет, разбивай вручную» (в отличие
    от дисперсии, которая перечисляет группы). Пороги размера ≈ count-p99
    корпуса (класс: 30 методов / WMC 200).
- **Решения реализации** (этап 1):
  - **Как определяем `dependency` без type checker'а:** (а) параметры
    конструктора с модификатором (`TSParameterProperty`: `private http: Http`);
    (б) поле, инициализированное `inject(...)` (Angular). Оба → член `dependency`,
    рёбер не создаёт. Это лечит именно тот false-positive ATFD, из-за которого мы
    отказались от PMD-гейта.
  - **Конструктор исключён из кластеризации** (по LCOM4), но его тело
    сканируется, чтобы собрать имена полей: `this.x = …` заводит член-поле,
    иначе поля, объявленные только в JS-стиле, потерялись бы.
  - **Гейт `minMembers` держим чувствительным** (12 для класса), а не по сырому
    count-p95 корпуса (=32). Точность даёт конъюнкция «группы ≥ 3 И Σ сложности»,
    поэтому высокий порог по членам не нужен и пропустил бы god-класс на 18
    методов с 4 явными группами.

### God Module

- **Статус**: канона нет — Java-литература класс-центрична. Это **наш перенос
  LCOM4 на область видимости модуля**: top-level функции = методы,
  module-level переменные = поля.
- **Прецеденты**: JSNose — Fard & Mesbah, *JSNose: Detecting JavaScript Code
  Smells* (SCAM 2013) — god/large object для JS; Designite (Sharma) — смелл
  *Multifaceted Abstraction*.
- **Детали**: поддеревья типов пропускаются (общий `Config`-интерфейс склеивал
  бы несвязанные кластеры); barrel-файлы исключены (реэкспорты = «много
  экспортов, ноль связности» by design); файлы < 5 членов не оцениваются
  (там метрика вырождена — та же проблема, что у TCC на мелких классах).
  Отдельный сигнал: несколько экспортируемых классов в одном файле.
- **Эвристики**: сам перенос на модуль + гейт (members ≥ 15, **групп** ≥ 3,
  Σcognitive ≥ 150). Числа — из count-перцентилей корпуса, помечены preliminary.
  Проверено на реальном коде: `generate-md-docs.ts` в svelte — 24 функции в 4
  группах (markdown / svelte / kbd / fences), вывод = готовый план распила.

### Пороги — методология калибровки

- **Теория**: Alves, Ypma, Visser, *Deriving Metric Thresholds from Benchmark
  Data* (ICSM 2010, методология SIG): пороги = перцентили распределения метрики
  по бенчмарк-корпусу с взвешиванием по LOC. Их результат: распределения таких
  метрик стабильны между доменами — поэтому корпус **должен** быть смешанным
  (React, Node, Angular, CLI, библиотеки), это условие метода, а не слабость.
  Lanza/Marinescu свои константы получили так же — но из Java/C++ корпуса,
  поэтому их числа не переносимы, а метод переносим.
- **Реализация**: `scripts/calibrate.ts`, корпус 22 open-source TS-репо
  (`clone-alert/bench/repos`), распределения публикуются в `docs/thresholds.md`.
- **Корректировка по итогам прогона (важно):** чистое LOC-взвешивание Alves для
  НАШЕЙ задачи даёт непригодные пороги — сложность p95 = 95, god-модуль
  minMembers = 1715. Причина: Alves-метод отвечает на вопрос «какая доля *объёма
  кода* лежит в сущностях выше порога», и длинные сущности одновременно
  сложнее и весомее по LOC — перцентиль уезжает вверх. Нам же нужен другой
  вопрос: «пометь худшие 1–5% *сущностей*». Поэтому:
  - дефолты берём из **count-перцентилей** (каждая сущность = 1 наблюдение,
    p95/p99 = «худшие 5%/1%»);
  - **LOC-взвешенную колонку Alves оставляем в отчёте как референс** — метод
    честно указан, но не является основой дефолтов.
  Числа сошлись здравые: сложность count p95 = 13, p99 = 38 (дефолт Sonar 15
  ложится ровно между — подтверждение, не противоречие).
- **Гигиена корпуса — тоже вывод прогона:** без фильтра бандлов один
  `webpack/bundle5.js` (сложность 82514, десятки тыс. LOC) перекашивал всё
  распределение. Поэтому обход режет тесты/фикстуры, `compiled`/`vendor`,
  сгенерированное (маркеры) и **бандлы по эвристике сверхдлинных строк**
  (> 2000 символов в строке) — см. «границы честности».

## Этап 2: интеграции (реализовано)

| Проверка | Движок | Заметки |
|---|---|---|
| Дубли | `clone-alert` (свой пакет, PMD CPD-совместимый) | группы клонов, дублированные строки |
| Мёртвый код | Knip через `knip/session` (программный API v6) | `stopslop.json#knip` — единственный конфиг; deps/exports уверенно, files — с оговоркой про entry points |

Оба входят через `analyzeProject(ctx)`, грузятся динамическим `import()` внутри
анализатора: падение или отсутствие движка → запись в `notes`, а не крах прогона.
Ядро компилируется и работает без них (`--fast`). Атрибуция в выводе обязательна.

### Решения, принятые при реализации

- **Оба движка едят наш список файлов, а не свой.** В `Cpd` подаются уже прочитанные
  исходники из `ParsedFile` (`addSource`), находки Knip фильтруются по множеству
  проанализированных путей. Иначе правила исключения расходятся: CPD начинает
  репортить клоны в тестах и генерённом коде, Knip — «неиспользуемые» фикстуры.
- **`ignoreIdentifiers: true` по умолчанию — и это ловит наш кейс.** Проверено на
  собственном коде: `childNodes` скопирован между `cognitive-complexity.ts` и
  `members.ts` с переименованным `isChild` → `isNode`. Точный матчер (дефолт PMD)
  проходит мимо; нормализация идентификаторов ловит. Копипаста с переименованием
  переменных — ровно то, что делает агент.
- **`minLines: 5` — цена этой чувствительности.** С нормализацией идентификаторов
  плотные однострочники (таблицы конфигов, длинные шаблонные строки) матчатся по
  токенам: на своём же репо 3 из 10 находок были 2-строчными кусками
  markdown-таблицы в `calibrate.ts`. Порог по физическим строкам (по самому
  «тесному» вхождению) их снимает, не трогая настоящие клоны. **Эвристика.**
- **Идентичность клона — отпечаток контента, не строки.** `symbol = clone:<sha1(spanImages)[0:10]>`
  через `Cpd.spanImages()`. Ключ `file + symbol` переживает сдвиг клона по файлу —
  это требование baseline-диффа этапа 3, где номера строк нестабильны.
- **Unused files = `info`, не `warn`.** Зависит от детекта entry points, который
  промахивается на проектах с нестандартными входами. Оговорка едет в самой находке
  (`data.caveat`), а не только в доке.
- **Knip запускается от корня пакета, а не от анализируемого пути.** `stopslop src/`
  → ищем ближайший `package.json` вверх, `cwd` = он, находки маппим обратно и режем
  по анализируемому корню. Нет `package.json` → в `notes`, проверка пропущена.
- **Knip-конфиг принадлежит StopSlop.** Полный JSON-совместимый конфиг находится
  в `stopslop.json#knip`; `knip.json`, `.knip.json`, `knip.config.*` и
  `package.json#knip` не загружаются как конфиг, не объединяются и не исполняются.
  Сам `package.json` всё ещё читается как manifest, но поле `knip` отбрасывается. Поскольку
  `createOptions` Knip даже при явном config делает merge с `package.json#knip`,
  адаптер сначала создаёт options в одноразовом bootstrap-каталоге с
  санитизированным manifest, затем переносит уже разобранные options на реальный
  package root. Это также исключает выполнение программного `knip.config.js`.
- **Workspaces остаются нативными Knip.** `knip.workspaces` передаётся без своей
  интерпретации (`.` = корень, glob-ключи = группы пакетов). Монорепо без этого
  поля показывает находки, но не включает сигнал dead code в score.
- **Schema — публичная граница настройки.** Корневой `schema.json` встраивает
  schema установленной версии Knip и публикуется в npm package. CLI не содержит
  init/wizard/эвристики генерации: анализ проекта и запись конфига — задача
  будущего MCP-сервера.
- **Нет `node_modules` при объявленных зависимостях → мёртвый код не считаем.**
  Без установки Knip не разрешает ни одного импорта: на gatsby без `node_modules`
  прогон дал 555+ «неиспользуемых» зависимостей. Это не находки, это сломанный
  прогон — отказываемся считать и пишем в `notes`. Важно для `npx stopslop` на
  свежем чекауте.
- **Диагностику Knip перехватываем.** Он пишет ошибки загрузки плагинов прямо в
  `console.error`; это его диагностика, а не наш отчёт. Перехватываем на время
  сессии и сворачиваем в одну строку `notes` с их числом.
- **«Не померили» ≠ «чисто».** Скор берёт сигналы дублей и мёртвого кода не из
  конфига, а из `ctx.metrics`: движок выставляет метрику, только если реально
  отработал. Иначе пропущенный Knip рисовал `dead code 0.00/KLOC` — репо получал
  бесплатный кредит за непроведённую проверку (поймано на gatsby).
- **Дубликаты и мёртвый код не удваивают AST-работу**: `analyzeProject` получает уже
  распарсенные файлы, второй проход по диску не делается.

### Slop level

Скор — взвешенная сумма **плотностей** (на KLOC; дубли — доля строк), каждая
насыщается на своём бюджете:
`score = 100 · Σ wᵢ·min(1, xᵢ/budgetᵢ) / Σ wᵢ`. Полная формула, веса, бюджеты и
их обоснование — в [docs/score.md](docs/score.md). Ключевые свойства: независимость
от размера репо, насыщение (один патологический файл не топит остальные оси),
**выключенная проверка выпадает из формулы, а не считается «чисто»**.

Статус: веса — оценочное суждение, бюджеты — якоря (10% дублей — общепринятая
граница jscpd/PMD; остальные привязаны к порогам детекции и калибровочному
корпусу), не перцентили. Помечены `preliminary` вместе с порогами. **Эвристика.**

## Границы честности (в README и вывод)

- Без type checker'а: разрешение ссылок — лексическое, по областям видимости.
  Модульный уровень — scope-walker со стеком областей (параметры, локальные
  объявления, деструктуризация, hoisting функций-деклараций); классовый —
  `this.<член>`. Динамика (`this[key]`, реэкспорты через барели, декораторы с
  побочными эффектами) не разрешается — метрики называем по-честному
  (`clusters`, `hubs`), полную семантику не обещаем.
- **Импорты модуля не члены**, а не «члены-`dependency`»: два метода, дёргающие
  один импорт, просто не создают ребра (импорт не в множестве членов). Тот же
  эффект, что у `dependency`-полей класса, без лишней сущности.
- Кластеры репортим поимённым составом, ярлыки («invoice generation») не
  придумываем — без LLM это невозможно, а с натяжкой поймают.
- Пороги до калибровки помечаются в выводе как preliminary.
- **AST**: `oxc-parser` даёт ESTree-подобные узлы с байтовыми/UTF-16 offset'ами
  без `loc` — номера строк считаем сами (индекс переносов на файл). Один
  `parseSync` на файл, дерево раздаётся всем анализаторам.

## Валидация на ИИ-генератах

Прогон на двух репозиториях, о которых известно, что они на 100%
сгенерированы ИИ-агентом (`codelore`, `vscode-angular-auto-import`),
воспроизвёл именно целевую сигнатуру слопа:

- `CodeloreService` — 60 методов, WMC 402, один компонент связности → **ось
  размера**. Дисперсия молчала: класс «честно связный», ровно как описал
  пользователь. Без оси размера утёк бы.
- `AngularIndexer` — 89 методов, WMC 341; `DiagnosticProvider` — 68 / 306 →
  **ось размера**.
- Плюс десятки функций выше порога когнитивной сложности.

Для контраста на хорошо факторизованной библиотеке (material-ui, 26k файлов)
god-классов **ноль** — инструмент не поднимает ложную тревогу на чистом коде.
Именно эти два кейса и мотивировали двухосевой детектор.
